## 정의

SaaS(Software as a Service)는 **클라우드 컴퓨팅 서비스 모델**로, 소프트웨어 공급자가 인터넷을 통해 완성된 애플리케이션을 제공하면서 기반 인프라·미들웨어·소프트웨어 유지보수를 모두 관리하는 방식이다. 사용자는 웹 브라우저로 접근하여 소프트웨어를 사용만 하며, 설치·업데이트·서버 관리가 불필요하다.

핵심 원리는 **"소프트웨어의 소유와 사용의 분리"**다. 소프트웨어를 구매하여 소유하는 것이 아니라, 서비스로 구독하여 사용한다.

## 핵심 특성

| 특성 | 설명 |
|------|------|
| **구독 기반 과금** | 영구 라이선스 대신 월/년 단위 구독료 |
| **멀티테넌시** | 단일 소프트웨어 인스턴스가 복수 고객(테넌트)을 서비스 |
| **자동 업데이트** | 벤더가 보안 패치·기능 업데이트를 중앙에서 관리 |
| **웹 기반 접근** | 설치 없이 브라우저·모바일 앱으로 즉시 사용 |
| **확장성** | 수요에 따라 사용자 수·스토리지 등 구독 수준 조정 |
| **API 기반 통합** | REST API 등으로 타사 시스템과 연동 |

## 클라우드 서비스 모델에서의 위치

클라우드 컴퓨팅은 관리 범위에 따라 세 가지 서비스 모델로 나뉜다:

```
┌──────────────────────────────────────────────────┐
│                  사용자 관리 범위                   │
├────────────┬────────────┬────────────┬────────────┤
│ On-Premise │   IaaS     │   PaaS     │   SaaS     │
├────────────┼────────────┼────────────┼────────────┤
│ 애플리케이션│ 애플리케이션│ 애플리케이션│            │
│ 미들웨어   │ 미들웨어   │            │            │
│ OS         │ OS         │            │  데이터만   │
│ 가상화     │            │            │  관리      │
│ 서버/스토리지│           │            │            │
│ 네트워킹   │            │            │            │
├────────────┼────────────┼────────────┼────────────┤
│  모두 관리  │ 인프라 위탁 │ 플랫폼 위탁 │ 전부 위탁  │
└────────────┴────────────┴────────────┴────────────┘
```

- **IaaS** (Infrastructure as a Service): 서버·스토리지·네트워크 제공. 사용자가 OS부터 관리. 예: AWS EC2, Azure VM
- **PaaS** (Platform as a Service): 개발 플랫폼 제공. 사용자는 코드·데이터만 관리. 예: Heroku, Google App Engine
- **SaaS** (Software as a Service): 완성된 애플리케이션 제공. 사용자는 데이터만 관리. 예: Gmail, Salesforce

> SaaS는 보통 PaaS나 IaaS 위에서 작동한다. 89% 기업이 복수 모델을 조합하는 멀티클라우드 전략을 사용한다.

## 아키텍처

### 멀티테넌시 (Multi-tenancy)

대부분의 SaaS는 **멀티테넌트 아키텍처**를 채택한다. 단일 소프트웨어 인스턴스가 모든 고객에게 서비스를 제공하되, 데이터는 논리적으로 격리된다.

리소스 할당 전략은 세 가지:

| 전략 | 설명 | 트레이드오프 |
|------|------|-------------|
| **공유 모델** | 모든 테넌트가 자원 공유 | 효율성↑ 비용↓ / 장애 영향 범위↑ |
| **사일로 모델** | 테넌트별 자원 완전 격리 | 보안↑ / 비용↑ |
| **혼합 모델** | 일부 공유 + 일부 격리 | 현실적 균형 (대부분의 SaaS) |

### 두 가지 평면

1. **애플리케이션 평면**: 핵심 비즈니스 로직. 테넌트 요청을 적절한 서비스로 라우팅
2. **컨트롤 평면**: 테넌트 온보딩, 청구, 메트릭 등 운영 시스템

## 수익 모델

| 모델 | 특징 | 대표 사례 |
|------|------|----------|
| **구독형** (Subscription) | 월/년 정기 결제. 가장 일반적 | Netflix, Salesforce |
| **종량제** (Usage-based) | 사용량(사용자 수, 거래량 등) 기반 과금 | AWS, Twilio |
| **프리미엄** (Freemium) | 기본 무료 + 고급 기능 유료 | Slack, Dropbox |
| **광고 기반** | 무료 서비스 + 광고 수익 | Gmail(무료 버전) |

> 영구 라이선스(perpetual license) 모델은 점점 인기를 잃고 있으며, 구독형·종량제가 SaaS의 주류 수익 모델이다.

## 역사 (요약)

- **1990년대**: ASP(Application Service Provider) 등장 — 고객별 별도 인스턴스, 수동 설정
- **1999**: Salesforce 창립 — "No Software" 슬로건으로 SaaS 대중화 선도
- **2004**: Gmail 출시 — 소비자 대상 첫 대규모 SaaS 제품
- **2020년대**: SaaS가 소프트웨어 배포의 주류. 2024년 시장 규모 $317B

## 장단점

### 장점
- **낮은 초기 비용**: 라이선스·인프라 투자 불필요
- **즉시 배포**: 설치·설정 없이 가입 즉시 사용
- **자동 유지보수**: 업데이트·보안 패치를 벤더가 관리
- **접근성**: 인터넷만 있으면 어디서든 사용
- **확장 유연성**: 사용자 수·기능 수준 자유롭게 조정
- **소규모 기업 접근성**: 높은 일회 비용 없이 엔터프라이즈급 소프트웨어 사용 가능

### 단점
- **인터넷 의존성**: 오프라인 시 서비스 불가
- **데이터 보안 우려**: 벤더의 보안 정책에 의존. 정부 데이터 요청 가능성
- **커스터마이징 제한**: 온프레미스 대비 맞춤 설정 범위 제한
- **벤더 종속(Lock-in)**: 데이터 이전·공급자 전환 비용
- **구독 피로**: 장기적 누적 비용. 가격 인상 리스크
- **네트워크 지연**: 온프레미스 대비 레이턴시 발생

## 비즈니스 메트릭

SaaS 비즈니스의 건강도를 측정하는 핵심 메트릭은 **수익**, **획득**, **유지** 세 영역으로 나뉜다.

### 수익 메트릭

| 메트릭 | 정의 | 계산 |
|--------|------|------|
| **MRR** (Monthly Recurring Revenue) | 월간 반복 수익 | 활성 구독의 월간 지불액 합계 |
| **ARR** (Annual Recurring Revenue) | 연간 반복 수익 | MRR × 12 |
| **ARPU** (Average Revenue Per User) | 사용자당 평균 수익 | MRR ÷ 활성 유료 고객 수 |

MRR은 5개 구성요소로 분해된다:
- **New MRR**: 신규 고객 수익
- **Expansion MRR**: 업그레이드/추가 상품 (획득비용 없는 성장)
- **Reactivation MRR**: 재가입 고객
- **Contraction MRR**: 다운그레이드 손실
- **Churn MRR**: 해지 손실

### 획득 메트릭

| 메트릭 | 정의 | 건강한 기준 |
|--------|------|-----------|
| **CAC** (Customer Acquisition Cost) | 신규 고객 1명 확보 비용 | — |
| **CAC Payback** | CAC 회수 기간 | < 12개월 |
| **LVR** (Lead Velocity Rate) | 월간 적격 리드 증가율 | 양(+)의 추세 |

CAC = 총 영업·마케팅 비용 ÷ 신규 고객 수

### 유지 메트릭

| 메트릭 | 정의 | 건강한 기준 |
|--------|------|-----------|
| **Churn Rate** | 고객/수익 이탈률 | 월간 < 5-7% |
| **LTV** (Customer Lifetime Value) | 고객 생애 가치 | — |
| **LTV:CAC** | 생애가치 대비 획득비 비율 | ≥ 3:1 |
| **NRR/NDR** (Net Revenue Retention) | 순수익 유지율 | > 100% |
| **NPS** (Net Promoter Score) | 순추천 지수 | — |

핵심 공식:
- **LTV** = 월간 고객당 MRR ÷ 월간 이탈률
- **NRR** = (유지 수익 + 확장 수익 - 축소·이탈 수익) ÷ 시작 수익 × 100

> **NRR > 100%**이면 신규 고객 없이도 매출이 성장한다는 의미다. 이는 제품-시장 적합도의 가장 강력한 신호.

### 메트릭 상호 관계

```
Churn ↓ → LTV ↑ → LTV:CAC ↑ → 공격적 획득 투자 가능
                                        ↓
Expansion ↑ → NRR > 100% ← ← ← ← 신규 획득 압력 감소
```

### 성장 단계별 우선순위

| 단계 | 우선 메트릭 |
|------|-----------|
| 초기 (PMF 탐색) | MRR 성장률, LVR, 전환율 |
| 성장 (스케일업) | Burn Multiple, CAC Payback, LTV:CAC |
| 성숙 (효율화) | Rule of 40 (성장률 + 순이익률 ≥ 40%), 총수익 마진 ≥ 75% |

## 성숙도 모델

Microsoft가 2006년에 제안한 **SaaS 아키텍처 성숙도 모델**은 멀티테넌시, 확장성, 구성 가능성 3축으로 4단계를 정의한다.

| 레벨 | 이름 | 멀티테넌시 | 확장성 | 구성 가능성 |
|------|------|-----------|--------|-----------|
| **L1** | Ad-hoc/Custom | 단일 테넌트, 고객별 별도 인스턴스 | 제한적 | 코드 수준 커스텀 |
| **L2** | Configurable | 고객별 인스턴스, 동일 코드베이스 | 향상 | 메타데이터 기반 설정 |
| **L3** | Multi-tenant | 단일 인스턴스, 복수 고객 서비스 | 로드 밸런싱 | 고급 커스터마이징 |
| **L4** | Scalable | 서버 팜 기반 동적 스케일링 | 무한 확장 | 완전 자동화 |

### 레벨별 대표 사례

- **L1**: 초기 SaaS 스타트업, 레거시 ASP 마이그레이션
- **L2**: Dropbox — 조직당 수백 사용자, 스토리지 분석
- **L3**: Salesforce — 수천 고객, 정교한 CRM 커스터마이징
- **L4**: Microsoft 365 — 전 세계 수백만 사용자, 종합 생산성 스위트

> Level 4에 도달한 기업은 전체의 **15-20%**에 불과하다. 대부분의 SaaS는 L2-L3 사이에 위치한다.

### L1에서 L4로의 핵심 진화

```
L1 (단일 테넌트)
 ↓ 코드 통일
L2 (동일 코드, 별도 인스턴스)
 ↓ 인스턴스 통합
L3 (단일 인스턴스, 멀티테넌트)
 ↓ 동적 스케일링
L4 (서버 팜, 무한 확장)
```

각 단계 전환의 핵심 과제:
- L1→L2: **코드 표준화** — 고객별 커스텀 코드를 설정(configuration)으로 대체
- L2→L3: **데이터 격리** — 단일 인스턴스에서 테넌트 간 데이터 안전하게 분리
- L3→L4: **무상태 설계** — 인스턴스를 동적으로 추가/제거할 수 있는 아키텍처

3. **혼합 모델** — 일부 공유 + 일부 격리 (대부분의 현실적 SaaS)

?

2. **종량제** (Usage-based) — 사용량 기반 과금 (AWS, Twilio)

SaaS Rule of 40이란?::성장률 + 순이익률 ≥ ==40%==. 성숙 단계 SaaS 기업의 건강도 판단 기준. 빠른 성장이면 낮은 이익률 허용, 느린 성장이면 높은 이익률 필요.

?

2. **Expansion MRR** — 업그레이드/추가 상품
3. **Reactivation MRR** — 재가입
